从 GitHub 下载、安装与换电脑

正式仓库：owner-workflow-kit，属于你自己的私有仓库。先登录有权限的 GitHub 账号。

  1. 第一次下载： 对 Agent 说下面这段话，或者打开仓库的 Releases 下载 ZIP，解压到独立工具目录。
  2. 安装： 双击解压目录里的 install.cmd。旧 Skill 会先备份；相同版本跳过。缺少 Backlog 时尝试安装官方版本，缺少 Node/npm 时提示 Agent 补齐。它不安装 Superpowers 或 Archify。
  3. 确认生效： 新开一轮或重启 Agent，确认两个 Skill 可被发现。不同软件的技能目录可能不同，让 Agent 检查，不要自己猜路径。
  4. 开始项目： 复制 新建项目启动词 或 接手旧项目启动词，填项目位置和目标。工具包不需要每个项目重新下载。
  5. 以后更新： 让 Agent 检查本地修改后安全拉取并重新安装。ZIP 不会自动更新；长期同步推荐由 Agent clone 仓库。
  6. 换电脑： 下载本工具包并安装，再拉取你自己的业务项目仓库。大型数据与仅在旧电脑上的产物需要单独迁移，Git 不会自动带走它们。

可直接复制：

从 https://github.com/shira-qwq/owner-workflow-kit 安装我的 Owner 工作方式。先检查已有副本和技能目录；已有修改不要覆盖，没有副本才下载到独立工具目录。读取 README，备份并安装两个 Skill，检查 Backlog 可用，确认当前 Agent 能发现技能。不要自动开始业务施工。

Backlog 软件从官方渠道安装；你的任务卡跟着自己的业务项目保存。 本工具包仓库只同步通用规则和指南，不收集各项目代码或数据。使用别人的项目时保留原始来源和许可证，把自己的工作同步到自己有权使用的独立仓库。

固定安装包：v1.0.0 下载页。安装入口仅支持 Windows；其他系统让 Agent 按 README 安装 Skill。安装并不等于所有业务项目已接入，项目入口和看板仍由首次启动步骤建立。

打开 可交互工作流程。你可以点击顶部三个场景，或点击 W01～W09 查看它们的连接；这些名称也能直接用于提问。完整文字含义见后文各章节。

2. 忘记调用 Skill 会怎样

正常使用时你不必每轮说 Skill 名。 Codex 支持根据描述自动选用 Skill；项目还应有短的工作入口提醒它使用 Backlog、读取当前任务并合理保存。官方 Skills 文档、项目规则文档

但必须满足三个条件：Skill 已安装且可发现；当前对话实际关联正确项目；宿主读到了项目入口。不同工具的加载方法可能不同，ZCode 的打包版本应实际检查，不能直接套用 Codex 的保证。

“自动选用”不是后台触发器，也不能保证模型百分之百不遗漏。如果你说“把这个功能修好”，即使忘记提 Skill，Agent 仍可能开始改代码；项目规则要让它同时维护任务和保存，而不是要求你背命令。若你自己手改了文件，Agent 只有下次核对时才能发现，不能假装一直看着文件。

第一次接入由 Agent 在项目已有规则中留下短入口并验证加载。以后若出现“代码改了但卡没更新”，说：

核对这次修改对应的任务、验证和保存状态，把遗漏补齐；不要重新做一遍。

防呆是降低遗漏成本，并让遗漏可发现、可补救；不靠额外常驻主控 Agent 保证一切。

3. 第一次启用与空白项目

先让 Agent 将本次两个正式 Skill 文件夹更新到实际使用的技能目录，保留原版并确认可发现。Project Control 必须连同 references 和 assets 一起使用。本轮还没有替你改用户级安装。

然后在项目目录开一个工作对话，说：

用 owner-project-control 初始化这里。我想解决的是……。先做最小可用结果，普通技术决定你自己做；不确定的新功能先研究或记 Draft。帮我打开任务看板。

Agent 应自行完成：确认目录、记录最小目标、准备 Git 和 Backlog、留下短项目入口、建立当前必要任务、实际启动并核对看板。目标清楚就继续已授权工作；遇到不同产品方向才问。

你最后应该拿到：可点击且名称正确的看板地址、一两句话说明当前目标、当前任务、下一步、保存状态。只给你一句“运行 backlog browser”不算把可达界面交付好。

本地看板关闭或电脑重启后，说“打开这个项目的看板”。Agent 找到实际项目和端口再启动，不要求你记命令；默认不安装开机服务。不同项目不能不经核对都指向同一个 6420 端口。

4. 接手别人的项目或旧项目

接手这个项目。我本次只想实现……。保留已有工作，先核对入口、任务、证据和相关版本；不要全仓考古，不要运行数据生产。

旧项目已经有规则、任务、图和研究结果时，Agent 接入它们，不新建一套同内容文档。首次认识陌生项目可以做与目标有关的最小摸底；它不等于审计全部源码和数据。

他人的开源项目要分清两件事：原项目已有能力，以及你本次希望改什么。原作者的全部路线图不是你的授权。原来的远端地址也不自动成为你的备份位置，Agent 不能擅自向他人仓库推送。

已有修改先保护。若版本、任务或证据冲突，Agent 应指出具体冲突并检查相关部分；无需因为局部不一致暂停所有无关工作。

你的 StoryLab 实际入口在 D:\StoryLab_CURRENT_PROJECT，不是本次消息中的旧路径。它已有数据全景、稳定名称、连接关系、来源范围与使用说明；本轮只定向读取这些入口，没有扫描数据盘或改项目。

5. 每天怎样用看板和 Draft

你的四张图中，第一张 Board 和第三张 Draft 是主要入口。第二张 All Tasks 方便检索。第四张 Statistics 只是任务统计：2/5 张卡完成并不代表产品完成 40%，更不能估计还需多少时间。

你想做什么 最省事的操作
想到新功能 在 Draft 填标题和一句目的，或直接告诉 Agent
不知道如何写卡 用对话描述，Agent 整理；实现计划不需要你填
想先看能否实现 说“先研究这张 Draft，别改正式产物”
想立即完成明确任务 说“完成这张卡”，或给出任务 ID
看为什么等你 打开 Review，Agent 应写明具体要你决定什么
看进度 看 In Progress 与当前卡结果摘要
只是想问为什么 直接在当前对话问，不必新建卡

第三张图在 Draft 表单里显示 To Do，并不因此代表已经批准开工。草稿容器和状态栏是两层含义。也不要把“Promote to Task”当自动执行按钮：进入正式任务后，仍需明确执行请求或已有执行约定。

网页编辑保存后，文件会由 Backlog 写入项目；你不必复制卡片回聊天。Agent 开工和写回前读取最新相关卡，避免用旧内容覆盖你的修改。单纯在网页中留言也不会唤醒未运行的 Agent，需要回到对话说“处理这张卡”。

你只需为新 Draft 写：想改善哪个功能、现在有什么不便、希望看到什么效果。其他字段可以由 Agent 补。不要把你变成表单录入员。

6. 边问边做：不用分三个窗口

一次对话可以这样发生：

  1. 你：“完成筛选功能。” → Agent 开始当前任务。
  2. 你：“这个筛选为什么这么慢？” → 回答当前问题，必要时在同一卡排查。
  3. 你：“再来个推荐系统怎么样？” → 简短评估、记录 Draft；不自动换目标。
  4. 你：“那先别做推荐，继续筛选。” → 沿当前任务继续。

对话不是工作类型。 Agent 应按每条输入判断，不把一个窗口永久定为闲聊、研究或施工，也不为每句话建任务。

默认一个正在施工的焦点。只有一个研究能独立推进、与当前改动不冲突时，才值得另开窗口；另开必须写明任务、可读写范围、所依据版本和结果位置。无需常设一个只管 Backlog 的管理员窗口。

7. 新想法、快研究与项目边界

你可以说：

我想到……。先查项目已有能力和成熟方案，判断是否值得做；不要直接搭完整系统。

Agent 先核对已有研究和当前目标。确实需要时才联网做有界检索，结果应回答：能改善什么功能、能复用什么、尚不确定什么、最小验证是什么、会增加什么投入。

快速研究可以停在“已有工具够了”“不值得做”“可以做但先试一个样本”或“证据不足”。不必为了证明工作量而生成完整计划、十张卡和原型。

在实质新增能力时默认优先查成熟方案；普通小修错不每次重搜。研究结束也不自动变成正式开发。你若说“就按这个做”，且范围清楚，Agent 记录批准后继续，不再同样问一遍。

每次扩大前守住一句话：这次只交付哪一个能用的结果，哪些东西明确留以后。 判断边界的是你，Agent 用证据和代价帮助你判断。不是先把所有想法做出来再寻找边界。

8. 研究到一半怎样保存

研究任务可以仍在进行中，却已经有可恢复的成果。无需新增“半研究完成”管理系统。

Agent 在原任务引用的研究记录里保存：正在回答的问题、已查来源与版本、已证实的结论、还缺的证据、失败方向及条件、样本和中间产物的位置、下一项检查。大日志放持久存储，报告只引用。

例如：

已确认工具 A 能读取本地数据；还未确认输出风格。已保留测试样本和配置，下次先看样本，不用重新搜工具。

暂停时，短 handoff 只引用这份研究和下一步。不抄一份完整研究结论。技术调查完成但假设不成立，研究卡也可以完成，正式功能仍不启动。

9. 开始施工和看实际效果

按刚才批准的最小范围完成这张卡，技术细节你决定；做好验证并保存。

Agent 负责必要的设计、实现、测试和记录。你看到的应主要是“哪个功能现在能用了、如何看效果、还有什么限制、是否需要你决定”。

Review 只用于你需要判断的产品效果或明确约定验收。技术测试不是让你充当测试员：Agent 应先完成检查，再把可评估结果给你。等待 Review 不得继续依赖该判断的施工，独立且已授权的工作可以继续。

结果不满意可以说“这个结果不接受，原因是……”。如果仍属于原验收标准，继续修当前任务；若要求新增结果，Agent 说明范围变化并更新批准记录。不要为了将卡标 Done 而改变你的验收含义。

10. 报错、撞墙与回头

你不需要先理解日志，也不需要立即另开调试窗口。说：

这个功能报错了。先判断影响范围，按当前任务排查；不要为了修错顺便重做系统。

Agent 应先说明用户能理解的影响，例如“导出暂时不能用，已有数据仍在”，再按实际证据排查。修当前施工导致的错误留当前卡；独立旧问题才建立必要新任务。

同一假设、相同输入、没有新证据时，不应重复执行相同方案。应缩小试验、读已有失败证据或换一个可验证假设。确实需要扩大投入、改变产品目标或不可逆操作时，再给你具体取舍。

回头不等于从零开始：先保留可用结果、当前失败点和中间数据；能恢复到已知可用版本就评估局部恢复。不能擅自丢弃其他窗口或你已有的修改。

错误也不应永远背在每轮上下文里。当前未解决且会导致重复踩坑的失败放 handoff 摘要；解决后移出当前摘要。长期有用的“在什么条件下失败、为何放弃”保留在原研究或任务记录。条件改变时可以重试，但要说明改变了什么。

11. Git 到底什么时候存档

用四种保存来理解：

保存 实际意义
文件写盘 草稿、代码或记录在本机文件里；通常不能据此回到更早版本
Git 保存点 为已纳入版本的文件保留一个能回去的版本
远端同步 已保存版本再放到配置好的远端；未同步就仍只有本机版本
数据检查点 长运行已经处理到哪里，下次怎样接着跑

Git 不自己定时干活，Skill 也不运行后台进程；Agent 正在工作时按规则替你操作。推荐保存时机：一个功能完成并验证、一个有价值的研究结论形成、重要中间结果需要暂停或交给下一个 Agent。未验证中间版本明确标注，不与“可用版本”混淆。

不是每改一张 Draft 都提交，也不是只有任务 Done 才允许保存。你忘记说“存档”不应影响 Agent 的正常职责。任务结束应告诉你“已保存可回滚版本”“当前是未验证中间版本”或“还有哪些修改未保存”。

Backlog 的 autoCommit 默认关闭；启用时针对任务记录变化，不会代替代码与数据的完整保存策略。本方案不默认开启逐次自动提交，也不设置拖卡即施工。官方配置

没有 Agent 工作时，你网页里新存的草稿可以已经写盘，但未必进入 Git 历史。下次 Agent 工作会检查保存；若你需要所有网页变更立刻有版本，那是另一个明确自动化需求，目前不默认添加。

大数据不必须进 Git。Git 保存脚本、小记录和必要证据索引；实际大数据、检查点在可靠存储。Git 回滚不自动回滚数据库或第三方副作用，Agent 必须另外判断恢复方法。

12. 换 Agent、断线与多个窗口

换人时说：

这是项目路径。接手当前任务，先核对证据和相关版本，从已有结果继续；不要重新研究没变的部分。

新 Agent 沿项目入口→当前 handoff→当前任务→任务直接引用的意图和证据→相关 Git 状态→必要文件读取。应回答：现在能否接手、依据哪个版本、哪些证据仍有效、第一步做什么。

已有证据足够且未变，直接继续；文件或输入变了，只重验受影响部分。关键证据缺失、不知道另一个 Agent 是否仍在写相同文件、目标发生冲突时，先解决这个具体问题。

正常暂停前 Agent 保存任务进度和证据；突然崩溃可能来不及写 handoff，这时从实际文件、任务和数据检查点恢复。不能承诺恢复从未保存的内存或聊天内容。

多个窗口时默认“一张卡一个写入负责人”。研究窗口可以读指定版本并写独立研究记录，施工窗口读其结论链接；若研究对象期间变化，明确结论适用的版本。跨机器还要确认文件和大数据可以访问。没有实际同步能力时，Backlog 不是实时消息总线。

13. 地图怎样使用，Archify 加不加

加作按需制图工具，不加作新主控或第二看板。 本次使用 Archify v2.16.0 的官方包生成示例，保存在审查工作目录；未全局安装。它能搜索名称与 ID、聚焦节点、追踪作者明确写入的连接、展示引导场景。Archify

它不负责拖动节点来改变程序运行。图中“有连接”也不自动证明生产环境真的用到了该数据，更不等于改一处一定会影响所有下游。Agent 必须先核实事实再写入图。

你可以按稳定名称下指令：

看图里的 W08，告诉我中间结果存在哪里。

对真实项目则用已有功能或数据 ID：

查看“Danbooru 标签词典”（DATA-DANBOORU-TAGS）目前服务哪些功能，按已有证据画局部图；不扫描整个数据盘。

我想修改“筛选结果”这个功能。先核对图与当前实现是否一致，再告诉我本次最小改动范围。

节点编号必须稳定，不能每次重画重新编号。图源或已有说明索引保留名称、功能用途、来源、相关任务与证据、依据版本。图本身不复制全部任务状态。Archify 原生聚焦卡主要展示图内关系，不能声称本例点击节点就自动打开任意 Backlog 卡或外部证据；这些关系通过已有项目索引和任务链接查找。

StoryLab 已有的更重要： docs/data/OWNER_DATA_ATLAS.html 是现成数据全景，事实来自已有 registry、edges 与资料说明。继续使用它；需要局部解释才生成 Archify 图。旧 Archify Owner-control 已归档，不恢复旧入口。当前文件的存在与说明已核对，本轮未对该 atlas 的全部点击交互或真实数据链做验证。

你无需学习图规范或亲手填 JSON，只需说“画出这个功能从输入到结果的过程，用人能理解的名字，标出未知和证据”。更新图时只更新受影响的说明和图源，不为重画而运行数据生产。

地图与本次 JSON 示例可以长期保存；HTML 是可重建的阅读结果。它丢了可以从图源生成，不需要重新研究项目。没有具体理解问题时，不要求每个项目先造全景地图。

14. 批量数据与长任务

处理这批数据。先确认输入和极小样本，再看代表样本质量与实测速度；在本次授权范围内扩大，保留断点，不覆盖原始数据。

你不必指定“必须先 10 条再 100 条”。样本依据内容多样性、风险和费用决定。若你只授权样本，Agent 不能自动全量；若全量已经授权且样本与投入符合标准，不需要你逐级批准。

没有实测速度时，Agent 应说“先测再估计”。开始后区分已成功、失败、重试和剩余，更新实际吞吐与预计剩余时间。总数不明就不编百分比。

恢复时核对输入、模型、Prompt 和配置；变了就不能直接混用旧结果。检查点保存已完成块和失败项，大量产物用持久位置，不只存在临时窗口。结果说明必须把运行成功、结构合格、语义抽样通过区分开。
