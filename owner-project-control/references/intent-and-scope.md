# 批准意图与范围变更

用于项目目标初始化、当前任务开工前核对，以及新想法、需求变化或疑似偏离时。不是独立 Skill，不提供另一套任务或规划流程。

## 一个当前意图入口

- 持续项目复用已有 PRD / Spec / 产品约定；没有才用 `docs/PROJECT-INTENT.md`。项目规则记录准确路径。目标通常一两屏能读完；复杂功能只引用必要的详细规格，不把全产品规格塞进入口。
- 它是“当前批准需求”的唯一入口，不是“当前实现状态”。有多个详细规格时，每条需求只在一处维护，入口只给链接；不要再保存同内容的另一份 Spec。
- 写明 Objective、用户场景、可判断的成功标准、In Scope、Out of Scope、约束、未决问题和批准依据。不要把 Agent 推测写成 Owner 决定。
- 已有产品不全仓逆向生成 Spec。先固定当前工作的已知意图；历史不明的部分标待确认，不据此阻塞无关且已明确的工作。
- 一个简单独立任务可以只用 Backlog 描述与验收条件，不强制建项目意图文件。持续项目的跨任务边界才需要单独持久入口。

## 判别新输入

先比较当前批准条款与任务验收条件，再判断新话语的意思，不按“顺便”“能不能”等词机械分类。

| 类型 | 判断依据 | 行动 |
| --- | --- | --- |
| 澄清 | 明确已有结果的含义，不改变对外承诺、成功标准或实质投入 | 修正相应表述，继续；若有两种不同产品含义才问 |
| 实现细节 | 在批准边界内选择实现方式，不新增用户能力或重要代价 | Agent 决定，不要求 Owner 选库或函数名 |
| 独立新需求 / 扩范围 | 新增用户、场景、输出、支持范围，或明显增加成本、时间、维护责任 | 说明与当前范围的差异；未授权先 Draft |
| 替换 / 收缩需求 | 原目标、规则或验收结果被取消或改变 | 核实替换的具体范围；已有明确指令就记录并执行，不再问一次 |
| 研究 / spike | 目的是验证可行性或价值，尚未承诺正式交付功能 | 有研究授权才开展有界验证；研究成功不自动生产化 |
| 暂时想法 | 只是提议、询问意见或请记录，没有执行授权 | 简短回答或捕获 Draft；不主动展开长研究或完整建设 |

修改很小不代表不是需求变化；实现很大也不一定是新需求。技术方案若引入外部数据发送、持续费用、关键体验变化或锁定性，就不再只是小技术选择。

本 Owner 偏好复用：新增有实质实现成本的能力时，先检查项目已有能力，再做与问题规模相称的官方方案 / 成熟项目检索；优先回答“能否复用、有什么缺口、最小验证是什么”。不为普通修错和已确定的小实现反复联网，不将一次快速检索自动扩为长研究。研究可以帮助确定可行边界，但不能替 Owner 批准产品边界。

## 批准与落盘

1. Owner 决定产品目标、真正范围和重要取舍；Agent 提案、分析、更新文件并在批准边界内施工。已有明确授权跨轮有效，不要求特定口令或仪式。
2. 对含糊且实质改变范围的输入，用短中文说明“当前批准什么、现在新增或替换什么、影响什么、建议如何处理”。必要时只问阻挡决定的核心问题。未得到答案不当作同意。
3. 新想法默认保存在 Backlog Draft；拒绝、搁置、批准可留在该条记录。不要复制到 handoff 的长期 Todo。Owner 要求不记录时不创建。
4. 批准变更后，先更新意图中相关条款，再通过 Backlog 工具更新受影响 Task 的验收条件、依赖与授权说明；明确撤销旧条件或标记旧任务已被替代，保留历史结果，不伪装成已完成。
5. 最小变更记录放受影响 Backlog Task 的 notes / decision 链接：日期、Owner 指令的准确摘要、原条款→新条款、理由、影响的任务及验证。指令已有清晰记录时引用即可，不建单独变更数据库；复杂长期决定才复用项目 decision 文档。
6. 文档与任务更新全部完成前不继续受影响施工；中断时在 handoff 标明“已批准，尚待同步哪些记录”。恢复时定向核对这些条目。
7. 每次任务完成时核对验收条件及相关意图条款。发现偏离，修实现或请求 Owner 批准改变要求；不能为通过验收而偷偷降低要求。Done 的历史记录不保证变更后的产品仍有效。

优先级调整只改变推荐顺序，不默认中断正在进行的工作或批准更多范围。“接受结果”和“同意扩大产品”是不同决定。

## 精简格式（复用已有等价文档优先）

采用 Spec Kit 的场景、需求、成功标准、假设结构；下列是中文适配格式，不是其命令生成物。只填写当前已知相关内容，不保留空栏目装饰。

```markdown
# 当前项目意图
批准依据：日期 + Owner 已明确指令摘要 / 持久记录链接；未批准部分明确标注

## Objective
为谁解决什么问题；相对现在的做法，什么改善值得做。

## User Scenarios & Testing
关键用户场景及可观察结果；可用“在……情况下，做……后，应……”表述。

## Requirements / Scope
当前批准做什么；明确不做什么。必要时给稳定需求编号供任务引用。

## Success Criteria
怎样才值得接受；产品成功标准在此，任务验证步骤放 Backlog，不复制。

## Constraints & Assumptions
已约定成本 / 时间投入边界、数据与体验约束；假设不要伪装成批准。

## Open Questions
尚未决定且影响当前边界的问题；提议不自动并入批准条款。
```

不在这里保存任务状态、实施步骤、历史流水账、测试日志或未来想法全集。当前正文随批准决定替换，历史由 Git 与原任务记录保留。

## 与成熟方案的关系

- [Spec Kit spec-template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)：采用用户场景、需求、可衡量结果和假设的结构理念；未复制其全文，不引入 feature branch 要求或三个固定故事。
- [Spec Kit persistence](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md)：选择 living spec 的“先更新批准规格，再调整派生工作”方向；这里保留 Backlog 的任务历史，不删除重建全部任务。
- [Backlog 维护者规则](https://github.com/MrLesk/Backlog.md/blob/main/AGENTS.md)：参考产品原则不可随实施偷偷改变、问题或提案不直接等于实施规格的实际做法。
- [Shape Up 的边界](https://basecamp.com/shapeup/1.2-chapter-03)：采用先判断值得投入多少的原则；不引入固定六周周期、额外看板或新会议制度。
- 本适配新增：Owner 批准依据、Draft 捕获、单一 Backlog、局部同步、中断恢复和不重复审批。这些是本 Owner 模式约定，不宣称为 Spec Kit 官方默认。

不安装完整 Spec Kit / OpenSpec；不运行它们的 plan、tasks、implementation 或任务同步扩展来复制 Backlog。Superpowers 的已批准设计可成为详细规格的唯一链接，计划保留一份即可。
